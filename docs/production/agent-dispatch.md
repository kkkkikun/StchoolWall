# 无人值守派活的价值闸门

本文件规定 `Agent dispatch` 工作流与 `.agent/dispatch-queue.json` 驱动的无人值守推进里，agent 如何自己判断「下一个任务值不值得做」。目的是让它在该停的时候停下来，而不是把同一主题反复切细、以维持队列不空。

## 循环是怎么转起来的

`.agent/dispatch-queue.json` 的 `current` 非空时，`Agent dispatch` 工作流开一张 @LL-ki 的派活 issue；agent 接单完成后自合并，并把**下一条**任务写回 `current` 随该 PR 提交；推 main 又触发工作流开下一张。引擎就是「agent 自己写下一条」，所以闸门必须落在写下一条之前，而不是事后审 PR。

## 判据

候选任务要同时满足下面五条，缺一条就不算「可安全完成的项」：

| 判据 | 要求 | 不达标的例子 |
|---|---|---|
| 有据 | 对应仓库里**已记录**的缺口：`openspec/specs/optimization/spec.md` 的待办条目、`openspec/changes/*/tasks.md` 的未勾选项、`docs/production/release-gates.md` 与 `docs/production/implementation-status.md` 里标为待验证的门禁、`.claude/docs/tasks.md` 的待办 | agent 自己想出来的「顺便改进」 |
| 有险 | 降低一个**已记录**的失败模式或风险：真实故障路径、真实失败模式、门禁未通过项 | 补一条指标名、补一段说明、对齐命名 |
| 不重复 | 同一主题（同一类信号 / 同一类守卫 / 同一类文档 / 同一份接入面）已经做过 ≥2 个类似 PR 的，不再切同类 | 把监控接入面一类一个信号地连续切 |
| 能做完 | 不需要人拍板、真实基础设施或平台审核就能完成并自证 | 真实告警确认、异机恢复、备案与商店准入 |
| 有净收益 | 预期减少的风险或工作量明显大于引入的改动量与后续维护成本 | 为凑一轮而做的低收益整理 |

依赖人工的项不是候选任务，但**必须**被记录成待人工验证条目（写明缺什么条件、谁来定），不能因为做不了就当作不存在。

## 不达标就停

最高优先级候选过不了判据时，agent 按下面三步做，这三步就是「该停」的完整动作：

1. **不写下一条**：把 `.agent/dispatch-queue.json` 的 `current` 置为 `null`（或删掉该字段），随当次 PR 提交。工作流读到空的 `current.id` 就不再派发，agent 转入空闲，不再自产任务。
2. **写清评估**：在当次 PR 说明与 `.claude/docs/tasks.md` 里写明评估过哪几个候选、每个为什么不达标、缺什么条件才能继续。评估要能被复核，不写「暂无合适任务」这种结论式的话。
3. **不凑数**：禁止把同一主题拆成多个 PR 反复做；禁止把补指标名、补说明、对齐命名这类低价值项当下一条任务；禁止为了让队列不空而制造任务。

停是正常结果，不是失败：已完成的条目照常交付、照常合并，只有「下一条」不写。

## 恢复条件

出现下面任一情况才继续推进：仓库出现新的**已记录**缺口（人写进 spec、runbook 或 tasks 的条目）、有人派活、待人工验证的项拿到了人工结论。恢复时从最高优先级的候选重新过一遍判据。

注意：`current` 置空只停派发，不停服务。agent 留在空闲态，人随时可以再派活；派活 issue 仍由 `Agent dispatch` 工作流按队列状态开出，不依赖 agent 自行启动。
